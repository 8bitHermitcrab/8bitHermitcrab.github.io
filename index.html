모델 선택 DECISION

문제
처음 적용한 BERT 모델의 정확도가 18%에 그침.
원인
당시에는 원인을 밝히지 못함. 18%는 가장 많은 토픽(세계, 16.7%)만 계속 고르는 수준과 비슷해, 모델이 사실상 학습되지 않은 상태였던 것으로 보임.
해결
한국어 사전학습 모델(klue-roberta-base)로 교체해 2022년 당시 정확도 95%를 기록했고, 영어는 DistilRoBERTa-base로 정확도 91%를 얻음.
돌아보며
지금이라면 모델을 바꾸기 전에 토크나이저가 한글을 제대로 나누는지(알 수 없는 토큰 [UNK]의 비율), 라벨 매핑이 맞는지, 학습률이 적절한지부터 확인했을 것.
재검증
2026년에 다시 보니 대회 테스트셋에는 정답 라벨이 없어 95%를 어떤 데이터로 측정했는지 확인할 수 없었음. 그래서 학습 데이터를 토픽 비율대로 8:2로 나눠 klue/roberta-base를 다시 학습하고, 서비스에 쓴 yobi 모델과 같은 검증셋으로 비교함. 결과는 아래와 같음.

fastapi-server

게시글 CRUD REST API 서버로, 유지보수하기 쉬운 구조와 트래픽 대응을 고민한 프로젝트

설계 DECISION

  • 데이터, 스키마, API 레이어를 분리해 계층 간 의존성을 낮춤.
  • 주석 없이도 읽히는 변수명과 함수명, RESTful한 URI 설계를 적용함.
  • Pytest로 응답 기대값과 DB 적재 여부를 검증하는 테스트를 작성함.

부하 테스트 METRIC

Locust로 게시물 조회 API에 동시 사용자를 1·2·4·16명으로 늘려 가며, 최적화를 하나씩 더할 때마다 같은 조건으로 RPS와 응답 시간을 측정함.

결과와 분석 DEBUG

문제
동시 사용자 16명에서 RPS가 약 600에 머물고, 평균 응답 시간이 1명일 때(약 10ms)보다 두 배로 늘어남.
시도
비동기 처리(asyncio), DB 커넥션 풀, uvicorn 워커 4개, Redis 연결을 차례로 추가함.
결과
16명 기준 RPS가 514~600으로 기본 구성과 큰 차이가 없었음. 사용자를 1,000명까지 늘리자 RPS는 약 470에서 더 오르지 않고 평균 응답 시간이 약 1,048ms까지 늘어나, 이 지점에서 서버가 포화됨을 확인함.
원인
코드를 다시 확인해 보니 Redis는 연결만 추가하고 조회 API에 캐시를 연결하지 않았음. DB는 MySQL이 아닌 SQLite 파일로 동작해 커넥션 풀의 효과가 거의 없었음. 조회 API는 기다리는 시간보다 객체 변환과 JSON 직렬화 같은 계산 비중이 커서 비동기 처리의 이점이 작았던 것으로 판단함.
배운 점
최적화를 추가한 뒤에는 실제로 적용됐는지 코드와 측정 결과로 함께 확인해야 함을 배움. 또한 병목 위치를 먼저 찾고 그에 맞는 방법을 골라야 함을 배움.

기존 신용카드 사용자의 개인정보로 신규 고객의 신용 등급(0~2)을 예측하는 웹 서비스로, 고객은 자신의 정보를 입력해 신용도를 조회하고 기업은 관리자 페이지에서 고객 데이터를 시각화해 분석함.

내 역할 · 데이터 시각화, XGBoost·LightGBM 모델링과 Optuna 튜닝, Streamlit 웹 구현과 EC2 배포, 내부 발표

데이터 특성 EDA

데이콘 '신용카드 사용자 연체 예측 AI 경진대회' 데이터(성별, 소득, 학력, 직업, 고용일수 등 개인정보)를 사용함. 타깃인 신용 등급(0이 가장 높음)이 2등급에 크게 치우쳐 있어, 정확도만으로 평가하면 성능을 과대평가하게 됨.

1 · 24%

발견
고용일수(DAYS_EMPLOYED)에 365,243일(약 1,000년)이라는 비정상 값이 약 4,400건 있음을 발견함.
원인
날짜 변수는 데이터 수집 시점(0)부터 거꾸로 센 음수로 기록되는데, 양수 값은 고용 이력이 없는 무직자에게 들어간 값이었음.
처리
양수 값은 0으로 바꾸고, DAYS_BIRTH·DAYS_EMPLOYED는 -365로 나누고 begin_month는 -1을 곱해 연·월 단위 양수로 변환함.
결측
직업(occyp_type) 변수의 결측치를 처음에는 제거했다가, 18개 직업을 BinaryEncoder로 인코딩한 뒤 KNN으로 예측해 채움. k 값을 바꿔 비교해 정확도가 가장 높은 k=3(정확도 0.868, 거리 가중)을 선택함.

파생변수 FEATURE

  • 고용 전 일수(before_EMPLOYED)와 소득 대비 비율, 고용 전 기간의 월·주 단위 변수
  • 가족 1인당 소득(income_mean), 나이와 근무연수 대비 소득(ability)
  • 생년과 고용 시점의 월·주 단위 변수
  • 모든 변수를 이어 붙여 만든 ID를 범주형 변수로 사용

모델 비교 METRIC

LightGBM, XGBoost, CatBoost를 비교해 범주형 변수를 자체 처리하고 기본 파라미터가 잘 최적화된 CatBoost가 가장 좋아 서비스 모델로 선택함. 직업 결측치를 KNN으로 채우자 세 모델 모두 log loss가 낮아짐.
